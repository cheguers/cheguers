\title{CheguersDB: an embedded graph--vector store with deterministic hybrid retrieval, and a controlled test of whether it helps AI agents}

\author[inteli]{Rafael Coutinho\corref{cor1}}

\address[inteli]{Instituto de Tecnologia e Lideran\c{c}a (Inteli), Av.\ Prof.\ Almeida Prado, 520, Butant\~a, S\~ao Paulo, SP, 05508-070, Brazil}

\cortext[cor1]{Corresponding author.}

\begin{abstract}
Hybrid retrieval-augmented generation (HybridRAG) combines vector similarity search with knowledge-graph traversal, and is usually built by joining a vector database and a graph database in application code. CheguersDB is an open-source, embedded TypeScript library that keeps records, typed relationships, JSON properties and embeddings in a single Turso database file. It answers hybrid queries (filter-first exact vector search, bounded graph expansion and a fixed weighted rerank) in a deterministic order, with the provenance of every result. On synthetic data with 10,000 records, a two-hop hybrid query takes 39~ms at the median, most of it in the exact vector scan. We also report a pre-registered evaluation of whether the store helps an AI agent answer relational questions. Over six seeded corpora, five question types and three repeats, an agent using CheguersDB was not more accurate than an agent that read the same data with Python, which reached an F1 of at least 0.92 on every question type. Graph expansion outperformed a vector-only ablation on two- and three-hop questions, but the difference did not survive correction for multiple tests. The evaluation harness, data and scorer are released with the software.
\end{abstract}

\section{Motivation and significance}
\label{sec:motivation}

Retrieval-augmented generation (RAG) conditions a language model on passages retrieved from an external corpus~\cite{lewis2020rag}. Dense vector retrieval finds passages that are semantically close to a question but ignores explicit relations between entities. Graph-based variants add those relations, either by building a knowledge graph from the corpus~\cite{edge2024graphrag} or by traversing an existing one~\cite{peng2025graphrag}. HybridRAG combines both, and on question answering over financial earnings-call transcripts it improved retrieval and answer quality over either approach alone~\cite{sarmah2024hybridrag}. Systems of this kind usually compose a vector store and a graph store.

That composition has four costs. Every hybrid query pays two client round-trips and the orchestration between them. The two stores keep separate commit logs, so an embedding can become visible before the record or the relationships it refers to. Two services must be deployed, backed up and upgraded. And the order of the retrieved context depends on two independently implemented rankers, which makes a RAG answer hard to regression-test.

Integrated systems exist. HelixDB~\cite{helixdb} is an open-source graph database with native vector search, K\`uzu~\cite{feng2023kuzu} is an embeddable graph database management system, and PostgreSQL with pgvector~\cite{pgvector} can combine vector similarity with relational joins. CheguersDB is a library rather than a server: it reuses an embedded SQL engine for durability, and it specifies its hybrid ranking exactly.

Software papers rarely measure whether an integrated store improves what an \emph{agent} does with the retrieved data. This paper makes three contributions:
\begin{enumerate}
  \item a single transactional store for records, labels, relationships and named vector namespaces, with a typed API that accepts no raw SQL and a deterministic hybrid retrieval procedure with provenance (\cref{sec:description});
  \item a latency characterization of exact search, traversal and hybrid queries (\cref{sec:latency});
  \item a pre-registered agent evaluation with an open harness and a seeded corpus generator with exact gold answers, whose results do not support the hypothesis that the store improves multi-hop agent accuracy in this setting (\cref{sec:agent}).
\end{enumerate}

\section{Software description}

\subsection{Software architecture}

CheguersDB is a pnpm workspace with three packages: \code{@cheguers/core} (the library), \code{@cheguers/cli} (a JSON command-line interface over the public API) and \code{@cheguers/benchmark} (the latency harness). The agent evaluation lives in \code{bench/agent-eval}. The core is written with Effect~\cite{effect}: every operation returns a typed effect whose error channel is one of \code{ValidationError}, \code{NotFoundError}, \code{ConflictError}, \code{DatabaseError} or \code{TransactionError}.

Persistence, write-ahead logging and recovery are delegated to Turso~\cite{turso}, an in-process SQL database that reimplements SQLite in Rust (\cref{fig:architecture}). An earlier prototype had its own storage engine; it was abandoned because a durable transactional store is not where the project's value lies.

The canonical schema has five tables. \code{records} holds a stable public identifier and a JSON body; \code{labels} and \code{record\_labels} attach labels to records; \code{relationships} stores typed directed edges with JSON properties, indexed on source, target, (source, type) and (target, type); and \code{vectors} stores one little-endian float32 BLOB per (record, namespace) pair, with one dimension per namespace (at most 4,096). Internal integer keys never cross the public API, and every user value reaches SQL as a bound parameter. Every public operation runs in one Turso transaction opened in immediate mode. A hybrid query therefore reads one consistent state of records, edges and vectors, and a multi-table write commits completely or not at all.

\subsection{Software functionalities}

\paragraph{Records, relationships and import} Records support create, read, update (a shallow JSON merge) and delete. A delete also removes the record's labels, vectors and incident relationships, in the same transaction. A nested JSON document can be imported as a tree of child records and relationships in one transaction.

\paragraph{Query language} Queries are JSON expressions with comparison, membership, string, existence and Boolean operators, plus related-record predicates of 1--3 hops. They are parsed into a validated syntax tree and compiled to parameterized SQL, with a deterministic tie-breaker.

\paragraph{Traversal} Bounded traversal of 0--3 hops has two strategies that return identical results: breadth-first search (BFS) over indexed adjacency queries, which is the default, and a recursive common table expression (CTE). Each hit reports its depth and, optionally, its paths.

\paragraph{Vector search} Search is exact. Label, property and graph predicates are compiled into the SQL that selects candidate rows, and a cosine or L2 distance is computed for each candidate in the host process. Ties are broken by public identifier.

\paragraph{Hybrid retrieval} A hybrid query $q$ takes:
\begin{itemize}
  \item a query vector and a metric;
  \item a seed count $k$ (default 10) and optional filters;
  \item an expansion depth $D \in \{0,1,2,3\}$ (default 1) and a direction (default both);
  \item optional relationship types with per-type weights $w_t \in [0,10]$;
  \item rerank weights $(\alpha,\beta,\gamma)$, default $(0.6, 0.3, 0.1)$, normalized to one;
  \item a result size $n$.
\end{itemize}
\textbf{Mode A} (filter, then vector search) is the case $D = 0$. \textbf{Mode B} (vector search, then graph expansion and rerank) follows \cref{alg:hybrid}. Each result carries its provenance: the seed of its best contribution and that contribution's value, the graph depth, the number of seeds that reached it, the final score, and a path summary such as \code{rec\_a --CITES--> rec\_b}. Filters apply to the seeds only, so expansion can reach records that do not satisfy them.

\begin{algorithm}[htbp]
\caption{Hybrid retrieval, Mode B, as implemented in \nolinkurl{packages/core/src/hybrid/service.ts}.}
\label{alg:hybrid}
\small
\begin{algorithmic}[1]
\State $S \gets$ filter-first exact top-$k$ for $q$
\State for each seed $i$: $s_i \gets 1 - d_i/2$ (cosine) or $1/(1+d_i)$ (L2); record $i$ as a candidate at depth 0
\State $F \gets \{(i, \mathrm{seed}_i, 1)\}$
\For{$\ell = 1, \dots, D$}
  \State fetch the edges incident to the nodes of $F$ in the chosen direction, in batches of 256
  \For{each state $(i, u, f) \in F$ and neighbour $v$, in (internal id, type) order}
    \State skip if $(i, v)$ was already expanded at level $\ell$ or \num{50000} states are reached
    \State $f' \gets f \cdot w_{t(u,v)}$; add the contribution $s_i\,\delta^{\ell} f'$ to $v$, with $\delta = 0.85$
    \State keep the first parent of $v$ for its path summary; push $(i, v, f')$ to $F'$
  \EndFor
  \State $F \gets F'$
\EndFor
\State for each candidate $v$: $b_v$ best contribution, $m_v$ minimum depth, $a_v$ distinct seeds reaching $v$
\State $\mathrm{score}(v) = \alpha\, b_v + \beta\,\frac{1}{1+m_v} + \gamma \min\!\left(1, \frac{a_v}{|S|}\right)$
\State \Return the top $n$ by score, ties broken by public id, with provenance
\end{algorithmic}
\end{algorithm}

\paragraph{Correctness} The repository contains 105 tests in 13 files (Vitest). Compiler golden tests fix the SQL text and the parameter order of each query form. Property-based tests with fast-check~\cite{fastcheck,claessen2000quickcheck} exercise the query parser and the nested-JSON normalizer. Differential tests~\cite{mckeeman1998differential} check that BFS and the recursive CTE return identical hits, depths and paths, including after the database is closed and reopened. Transaction tests check rollback across all mutation types.

const program = Effect.gen(function* () {
  const db = yield* open("./kb.db");
  yield* db.transaction((ops) => Effect.gen(function* () {
    const paper = yield* ops.records.create({ id: "paper-rag-2020",

    const survey = yield* ops.records.create({ id: "survey-graphrag",

    yield* ops.relationships.create({ type: "CITES",
      sourceId: survey.id, targetId: paper.id });

    yield* ops.vectors.upsert({ recordId: survey.id, vector: [0.2, 0.9, 0.1] });
  }));
  const hits = yield* db.hybrid.search({ vector: [0.1, 1.0, 0.0],
    metric: "cosine", seeds: 1, expandDepth: 1, topN: 5,
    includeProvenance: true });
  // hits[1].provenance: { seedId: "survey-graphrag", graphDepth: 1, pathCount: 1,
  //   pathSummary: "survey-graphrag --CITES--> paper-rag-2020" }
  yield* db.close;
  return hits;
});

\subsection{Latency}
\label{sec:latency}

The latency harness, \nolinkurl{packages/benchmark/src/run.ts}, creates a fresh database and generates a synthetic dataset from a linear congruential generator with seed 42. The graph is a chain $r_i \to r_{i+1}$ plus 24 edges from $r_0$ to $r_1,\dots,r_{24}$. Each record has a vector of dimension $d$ in namespace \code{default} and one of dimension $4d$ in \code{wide}. Each scenario runs 5 discarded warm-up executions and 50 measured executions, one at a time in one process. Percentiles use the nearest-rank method, so p95 and p99 rest on the three largest observations; following~\cite{hoefler2015benchmarking}, medians are the main statistic. The runs used an Apple M5 (10 cores, 16~GB RAM, macOS) with Node.js 24.13.0, at $N \in \{2{,}500, 10{,}000\}$ records with $d = 128$. Ingestion and storage figures, including $d = 384$, are in \cref{tab:ingestion} (\ref{app:tables}).

\Cref{tab:latency,tab:ingestion} and \cref{fig:scaling} show five things.
\begin{itemize}
  \item \emph{The exact vector scan dominates.} Multiplying $N$ by four multiplies the median search time by 4.2 (8.03 to 33.95~ms), as an $O(N)$ scan predicts. Switching to L2 lowers the median by 4--6\%, and raising $k$ from 10 to 100 raises it by 2--17\%.
  \item \emph{Graph expansion is cheap.} A two-hop Mode B query costs 2.4~ms more than plain search at 2,500 records and 5.0~ms more at 10,000. These are differences between separately measured scenarios, not per-stage timings.
  \item \emph{BFS is the right default.} At 10,000 records it is 7.0 times faster than the recursive CTE at two hops and 13.1 times faster at three, and the CTE's cost grows with $N$ while BFS stays nearly flat.
  \item \emph{An unselective filter is pure overhead.} The benchmark's label filter matches every record, so filtered search is 2--7.5~ms slower than unfiltered search. The gain from a selective filter is not measured here.
  \item \emph{Ingestion and storage are not the bottleneck.} Single creates sustain 7,300--7,900 records/s and batches of 25 sustain 13,600--15,200 records/s. The database file is 2.0 times the raw vector bytes at $d = 128$ and 1.4 times at $d = 384$.
\end{itemize}
These results have known limits. The vectors are synthetic and carry no semantic structure, so they concern cost, not retrieval quality. The graph is a chain with one 24-edge hub, so traversal frontiers stay small whatever the value of $N$. Each configuration was run once, so variation between runs is not quantified, and bulk throughput comes from two batches. Tail values above 390~ms are single observations whose cause was not investigated, and the resident memory in \cref{tab:ingestion} includes the Node.js runtime and the native Turso library. All results come from one machine.

\subsection{Agent evaluation}
\label{sec:agent}

The last example gives the store to an AI agent as a tool and asks whether an agent that answers relational retrieval questions with CheguersDB is more accurate than one without a database, or with a plain relational store. The study was pre-registered (\nolinkurl{bench/agent-eval/spec/PREREG.md}) before any agent trial ran.

\paragraph{Corpus and questions} A seeded generator builds a corpus of 1,400 papers, 700 authors, 80 organizations and 40 venues: 2,220 records and about 8,500 typed edges (\code{PRESENTED\_AT}, \code{AUTHORED\_BY}, \code{AFFILIATED\_WITH}, \code{CITES}). Each record's text states its relations in prose, so the same facts are available to every arm. About a quarter of the papers reuse the topic and setting of another paper, and about 30\% of the organization names are near-variants of another name. Questions are paraphrased with words that do not occur in the corpus. Five strata differ by the path from the question to the answer:
\begin{itemize}
  \item \emph{hop0}: a paper described by its topic, setting and modifier;
  \item \emph{hop1}: that paper's venue;
  \item \emph{hop2}: the organizations of its authors;
  \item \emph{hop3}: the organizations of the authors of the papers it cites;
  \item \emph{filter}: venue and affiliation name filters followed by a two-hop traversal.
\end{itemize}
Gold answers are computed from the graph; the hop2 and filter answers are also checked by a second computation over the same edges. The gold file enters a task only at scoring time, so the agent never sees it. A scenario is one seed and one stratum with five questions. Six seeds give 30 scenarios, so each main arm answers 150 questions per repeat and 450 over three repeats.

\paragraph{Arms} Every arm uses the same model (\code{claude-haiku-5-5} in Claude Code), corpus, questions, embedding function and a 12-turn budget, inside Terminal-Bench~\cite{merrill2026terminalbench} 0.1.1 containers.
\begin{itemize}
  \item \code{files}: the corpus as a JSON Lines file, with Python and grep.
  \item \code{sqlite3}: the same records, edges and vectors in SQLite tables, through Python's \code{sqlite3} module.
  \item \code{cheguers-full}: the \code{cheguers} CLI, whose use is mandatory, with \code{hybrid} at expansion depth 1.
  \item \code{cheguers-vector}: the same CLI restricted to vector search and depth 0, an ablation of graph expansion.
  \item \code{closed-book} and \code{gold-context}: calibration arms with no data, and with only the supporting records of each question.
\end{itemize}
The database arms load the data at install time, and the store directory is deleted before the agent starts, so they cannot read the relations as text. All arms embed text with all-MiniLM-L6-v2~\cite{reimers2019sbert} (384 dimensions, through \code{fastembed} 0.9.0). Corpus vectors are precomputed, and the model is baked into the base container image, so the embedder is identical in every arm. The main arms ran three times and the calibration arms once, with two containers in parallel. Before the study, the oracle agent, which writes the gold answers, passed all four variants of one task (\code{kb-s1-hop1}). The other tasks are built by the same script and were not run with the oracle.

\paragraph{Hypotheses and scoring} The primary metric is the per-question set F1 between the agent's answer and the gold set. Three one-sided hypotheses were pre-registered:
\begin{itemize}
  \item \textbf{H1}: \code{cheguers-full} beats \code{files} on hop2, hop3 and filter.
  \item \textbf{H2}: \code{cheguers-full} beats \code{cheguers-vector} on hop2 and hop3.
  \item \textbf{H3}: \code{cheguers-full} is no worse than \code{files} on hop0.
\end{itemize}
H2 also predicts no difference on hop0 and hop1. That part was not tested separately, and those strata are reported in \cref{tab:f1}. Repeats are averaged within each scenario. Differences are tested with a paired sign-flip permutation test over scenarios, with Holm correction~\cite{holm1979} across the six comparisons.

Each agent writes its answers to a file, and a hidden test computes F1 per question. The 12-turn budget is enforced with the \code{--max-turns} flag of the Claude CLI. A trial that exhausts the budget keeps whatever answers it wrote, and its unanswered questions score zero. Budget exhaustion is therefore counted separately, and it is a confound for accuracy, not a neutral failure. The budget was chosen in a pilot. At six turns every arm ran out before answering. At twelve, \code{files}, \code{sqlite3} and \code{cheguers-full} solved the pilot's hardest scenario, while \code{cheguers-vector} still ran out.

\paragraph{Results} \Cref{tab:f1,tab:tests} give the results. The calibration arms bound the task: the closed-book arm scores zero, so the answers cannot be guessed, and the gold-context arm scores 0.83--1.00, so the supporting records suffice. The \code{files} arm scores at least 0.92 on every stratum. H1 is not supported: \code{cheguers-full} is lower than \code{files} by 0.11 on hop2, 0.24 on hop3 and 0.11 on filter. H2 holds only before correction: graph expansion beats the vector-only arm by 0.61 on hop2 ($p = 0.015$, $p_{\mathrm{Holm}} = 0.089$) and 0.42 on hop3 ($p = 0.032$, $p_{\mathrm{Holm}} = 0.16$). H3 holds: \code{cheguers-full} scores 1.00 on hop0. Without expansion, the vector-only arm falls from 0.94 on hop0 to 0.28 on hop2, 0.26 on hop3 and 0.15 on filter. \code{cheguers-full} averages 6.9 to 8.8 CLI calls per question, and \code{cheguers-vector} 8.3 to 10.2. The gold-context ceiling is not perfect (exact-match rate 0.67 on hop1 and 0.83 on hop3), but those misses are not caused by missing evidence, because every gold answer is in the supplied records. The two CLI arms exhausted the turn budget most often, \code{cheguers-vector} in 56 trials and \code{cheguers-full} in 31, against one trial for \code{files} and none for \code{sqlite3} (\cref{tab:failures}). An offline retrieval gate run before the study found identical recall at 20 for vector and hybrid retrieval in every stratum (\cref{tab:gate}).

\paragraph{Why the baseline is strong} The \code{files} agent writes a short Python program that loads the corpus, matches the paraphrased question to a paper by its structured fields, and walks the relations in code. The model performs the semantic step, mapping the paraphrase to the corpus terms, and the join is exact. At 2,220 records this is a small computation for one process, so the corpus never forces a retrieval step, and the store has no room to add accuracy.

\paragraph{What the database adds} In this setting the database does not improve accuracy, and it costs more calls. Graph expansion helps over vector-only retrieval on the strata where vector search alone fails. Part of that gap is a budget effect, however: the vector-only arm runs out of turns most often, and this design cannot separate the two.

\paragraph{What would test the claim} A fair test needs data that the baseline cannot join in one pass. Examples are a corpus too large to load into one agent context or one process, selective filters, documents that do not reduce to a structured file, and a public multi-hop question-answering set with gold supporting facts. Such a test must be pre-registered and must not reuse the present gold data. The result is compatible with HybridRAG's reported gains on unstructured earnings-call transcripts~\cite{sarmah2024hybridrag}, which a script cannot join. The benefit of hybrid retrieval may depend on whether the relevant structure can be recovered without retrieval.

\paragraph{Threats to validity} Six scenarios per stratum give limited power. The intervals in \cref{tab:f1} are wide, and no comparison survives correction, so the data support ``no evidence of benefit under these conditions'' and a suggestive ablation effect, not effect sizes that generalize. Accuracy at a different turn budget could differ, and the budget was not varied. The \code{files} arm scores at least 0.92 on every stratum, which leaves little room for a better arm to show an improvement. The corpus is generated, not drawn from a public dataset, and the study used one model, one generator, one scorer and one embedder, so the results may not transfer to other models, corpora or embedders.

\paragraph{Deviations from the pre-registration} The pre-registration lists each deviation in full. In summary:
\begin{itemize}
  \item the embedder was not fixed in the draft; a lexical hash embedder put every arm at ceiling in the first pilot, and all-MiniLM-L6-v2 replaced it before the reported runs;
  \item the CLI has no bulk relationship command, so the loader uses the library's bulk API;
  \item a first full run placed the corpus inside the database-arm images, so those arms could read the relations as text; it is archived and excluded from every number here;
  \item the 12-turn budget was added before the reported runs;
  \item the planned retrieval-only comparisons (BM25, MRR, brute-force cosine) were not implemented, so the retrieval evidence is the top-20 proxy only;
  \item the \code{sqlite3} arm uses Python's \code{sqlite3} module rather than the \code{sqlite3} command-line tool;
  \item Holm correction is applied across all six tests, which is stricter than the draft's scheme;
  \item the CLI ignores \code{--direction outgoing}, which was documented and not fixed.
\end{itemize}

\section{Impact}
\label{sec:impact}

\paragraph{Reproducible retrieval for RAG} The hybrid order is fully specified, and every result carries its provenance. An application can therefore store the expected context for a set of questions and test that a change to its data or code does not silently change it.

\paragraph{Embedded memory for agents} The store is a single file inside the application process, so it can serve as persistent memory for local tools with no service to operate. This study does not show that it improves answers over plain files for the task tested.

\paragraph{A research baseline for agent retrieval} The harness, the seeded generator and the gold computation are a reproducible starting point for measuring agents on relational retrieval. The gold answers are computed from the graph, not written by hand. The study also shows why a strong code-reading baseline belongs in such evaluations.

%% ======================================================================
\section{Conclusions}
\label{sec:conclusions}

CheguersDB puts the parts of a HybridRAG retriever that are usually spread over two databases into one embedded library over one transactional file. Its ranking is deterministic and explains each result, and its costs are measured. At 10,000 records, traversal takes 1--2~ms, while exact vector search takes about 34~ms and grows linearly with the corpus. In a pre-registered agent evaluation on synthetic relational questions, the store did not improve accuracy over an agent that reads the same data with Python, and the advantage of graph expansion over vector-only retrieval did not survive correction.

Next steps follow from these limits:
\begin{itemize}
  \item a rebuildable approximate vector index, with exact search kept as fallback and recall reference;
  \item filters applied at every expansion hop;
  \item a concurrent read path;
  \item an agent evaluation in a setting where retrieval is necessary: corpora too large to load in one pass, selective filters, and a public multi-hop question-answering set.
\end{itemize}
