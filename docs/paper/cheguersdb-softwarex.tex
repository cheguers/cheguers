\title{CheguersDB: an embedded graph--vector store with deterministic hybrid retrieval, and a controlled agent evaluation of whether it helps}

\author[inteli]{Rafael Coutinho\corref{cor1}}
\ead{rafaelcouto111@gmail.com}
\author[inteli]{Davi Arantes}
\author[inteli]{Kaleb Isaias}
\author[inteli]{Jos\'e Romualdo}

\address[inteli]{Instituto de Tecnologia e Lideran\c{c}a (Inteli), S\~ao Paulo, SP, Brazil}

\cortext[cor1]{Corresponding author.}

\begin{abstract}
Hybrid retrieval-augmented generation (HybridRAG) combines vector similarity search with knowledge-graph traversal, and is usually built by composing a vector database and a graph database in application code. CheguersDB is an open-source, embedded TypeScript library that stores records, labels, typed relationships, JSON properties and embeddings in one Turso database file, and runs a hybrid query (filter-first exact vector search, bounded graph expansion and a fixed weighted rerank) with a deterministic ordering and per-result provenance. We describe the software and characterize its latency on synthetic data (median \SI{39}{ms} for a 2-hop hybrid query over \num{10000} records). We then ask whether the hybrid store helps an AI agent answer relational retrieval questions. In a pre-registered, controlled comparison run inside Terminal-Bench containers with \texttt{claude-haiku-5-5}, four main arms (files only, SQLite, CheguersDB with graph expansion, and CheguersDB vector-only) and two calibration arms answered relational questions over six seeded synthetic corpora in five strata, with three repeats. The files-plus-Python arm scored between \num{0.92} and \num{1.00} F1 on every stratum. CheguersDB with graph expansion scored lower on hop1, hop2, hop3 and filter, and higher on hop0 by a difference that is not significant. Against the vector-only ablation, graph expansion was better on hop2 and hop3, with nominal $p < 0.05$ that did not survive correction across the six pre-registered tests. The vector-only arm mostly exhausted its turn budget on multi-hop questions. Under these conditions the data show no benefit of the hybrid store over a baseline that can read the same data in code. The result does not show that the store is harmful in general.
\end{abstract}

\section{Motivation and significance}
\label{sec:motivation}

Retrieval-augmented generation (RAG) conditions a language model on passages retrieved from an external corpus~\cite{lewis2020rag}. Dense vector retrieval finds passages that are semantically close to a question but ignores explicit relations between entities. Graph-based variants add those relations, either by building a knowledge graph from the corpus~\cite{edge2024graphrag} or by traversing an existing one~\cite{peng2025graphrag}. HybridRAG combines both; on question answering over financial earnings-call transcripts it has been reported to improve retrieval and answer quality over either approach alone~\cite{sarmah2024hybridrag}. Those reported gains come from systems that compose a vector store and a graph store.

Composing two systems has four costs. Each hybrid query pays two client round-trips and orchestration. The two stores have separate commit logs, so an embedding can be visible while the record or relationships it refers to are not. Two services must be deployed, backed up and upgraded. And the order of retrieved context depends on two independently implemented rankers, which makes a RAG answer hard to regression-test.

Integrated systems exist. HelixDB~\cite{helixdb} is an open-source graph database with native vector search; K\`uzu~\cite{feng2023kuzu} is an embeddable graph database management system; PostgreSQL with pgvector~\cite{pgvector} can combine vector similarity with relational joins. CheguersDB is a library rather than a server. It reuses an embedded SQL engine for durability and specifies its hybrid ranking procedure exactly.

Whether an integrated store improves what an agent \emph{does} with retrieved data is a separate question, and the software literature rarely measures it. The benchmark vectors used for latency are synthetic and say nothing about retrieval quality, so this paper adds the missing evaluation. It is a controlled study of agent answer accuracy, pre-registered before the agent trials ran.

This paper contributes:
\begin{enumerate}
  \item a description of a single transactional store for records, labels, relationships and named vector namespaces, with a typed API that accepts no raw SQL, and a deterministic hybrid retrieval procedure with provenance (\cref{sec:description});
  \item a latency characterization of exact search, traversal and hybrid queries on one machine (\cref{sec:characterization});
  \item a pre-registered agent evaluation with four arms, a seeded synthetic corpus generator with exact gold answers, and an open harness (\cref{sec:design});
  \item results that do not support the hypothesis that CheguersDB improves multi-hop agent accuracy in this setting, together with the threats and deviations that bound what the result means (\cref{sec:results,sec:discussion}).
\end{enumerate}

\section{Software description}
\label{sec:description}

\subsection{Software architecture}

CheguersDB is a pnpm workspace with three packages: \code{@cheguers/core} (the library), \code{@cheguers/cli} (a JSON command-line interface over the public API), and \code{@cheguers/benchmark} (the latency harness). The core is written with Effect~\cite{effect}: every operation returns a typed effect whose error channel is one of \code{ValidationError}, \code{NotFoundError}, \code{ConflictError}, \code{DatabaseError} or \code{TransactionError}.

\Cref{fig:architecture} shows the layers. Persistence, write-ahead logging and recovery are delegated to Turso~\cite{turso}, an in-process SQL database that reimplements SQLite in Rust. Turso was chosen over a custom storage engine, which an earlier prototype used and which was abandoned, because a durable transactional store is not where the project's value lies.

The canonical schema has five tables. \code{records} holds a stable public identifier and a JSON body. \code{labels} and \code{record\_labels} attach labels to records. \code{relationships} stores typed directed edges with JSON properties, indexed on source, target, (source, type) and (target, type). \code{vectors} stores one little-endian float32 BLOB per (record, namespace) pair; all vectors in a namespace share one dimension (at most \num{4096}). Internal integer keys never cross the public API, and every user value is passed to SQL as a bound parameter.

All public operations run inside one Turso transaction opened in immediate mode, so a hybrid query reads one consistent state of records, edges and vectors, and a multi-table write commits completely or not at all.

\subsection{Software functionalities}

\paragraph{Records, relationships and import} Records support create, read, update (shallow JSON merge) and delete; deletion removes the record's labels, vectors and incident relationships in the same transaction. Nested JSON documents can be imported as a tree of child records and relationships in one transaction.

\paragraph{Query language} Queries are JSON expressions with comparison, membership, string, existence and Boolean operators, plus related-record predicates of 1--3 hops. They are parsed into a validated abstract syntax tree and compiled to parameterized SQL, with a deterministic tie-breaker.

\paragraph{Traversal} Bounded traversal of 0--3 hops is available in two strategies with identical results: breadth-first search over indexed adjacency queries (the default), and a recursive common table expression. Each hit reports its depth and, optionally, its paths.

\paragraph{Vector search} Search is exact. Label, property and graph predicates are compiled into the SQL that selects candidate rows; a cosine or L2 distance is then computed for each candidate in the host process. Ties are broken by public identifier, and the top $k \le \num{10000}$ are returned.

\subsection{Hybrid retrieval}
\label{sec:hybrid}

A hybrid query $q$ takes a query vector, a metric, a seed count $k$ (default 10), optional filters, an expansion depth $D \in \{0,1,2,3\}$ (default 1), a direction (default both), optional relationship types with per-type weights $w_t \in [0,10]$, rerank weights $(\alpha,\beta,\gamma)$ (default $(0.6, 0.3, 0.1)$, normalized to one) and a result size $n$. \textbf{Mode A} (filter$\to$vector) is the case $D = 0$. \textbf{Mode B} (vector$\to$graph$\to$rerank) uses $D \ge 1$ and follows \cref{alg:hybrid}.

\begin{algorithm}[t]
\caption{Hybrid retrieval, Mode B (\code{packages/core/src/hybrid/service.ts}).}
\label{alg:hybrid}
\small
\begin{algorithmic}[1]
\State $S \gets$ filter-first exact top-$k$ for $q$; for each seed $i$, $s_i \gets 1 - d_i/2$ (cosine) or $1/(1+d_i)$ (L2)
\State record each seed $i$ as a candidate with contribution $s_i$ at depth 0
\State $F \gets \{(i, \mathrm{seed}_i, \text{factor } 1)\}$
\For{$\ell = 1, \dots, D$}
  \State fetch edges incident to the nodes of $F$ in the chosen direction, in batches of 256
  \For{each state $(i, u, f) \in F$, neighbours $v$ sorted by (internal id, type)}
    \State skip if $(i, v)$ already expanded at level $\ell$ or \num{50000} states reached
    \State $f' \gets f \cdot w_{t(u,v)}$; add contribution $s_i\,\delta^{\ell} f'$ for $v$ with $\delta = 0.85$
    \State keep the first parent of $v$ for its path summary; push $(i, v, f')$ to $F'$
  \EndFor
  \State $F \gets F'$
\EndFor
\State for each candidate $v$: $b_v$ = best contribution, $m_v$ = minimum depth, $a_v$ = distinct seeds reaching $v$
\State $\mathrm{score}(v) = \alpha\, b_v + \beta\,\frac{1}{1+m_v} + \gamma \min\!\left(1, \frac{a_v}{|S|}\right)$
\State \Return top $n$ by score, ties broken by public id, with provenance
\end{algorithmic}
\end{algorithm}

For each result, the provenance reports the seed of its best contribution, that contribution's value, the graph depth, the number of seeds that reached it, the final score, and a path summary such as \code{rec\_a --CITES--> rec\_b}. Filters apply to the seeds only; expansion can reach records that do not satisfy them.

\subsection{Correctness strategy}

The repository contains 105 tests in 13 files (Vitest). Compiler golden tests fix the SQL text and parameter order for each query form. Property-based tests with fast-check~\cite{fastcheck,claessen2000quickcheck} exercise the query parser and the nested-JSON normalizer. Following differential testing~\cite{mckeeman1998differential}, tests check that the BFS and recursive-CTE traversal strategies return identical hits, depths and paths, including after the database is closed and reopened. Transaction tests check rollback across all mutation types.

\section{Illustrative example}
\label{sec:example}

\Cref{lst:example} stores two linked documents with embeddings in one transaction and runs a 1-hop Mode B query with provenance. The CLI exposes the same operation as \code{cheguers hybrid <db> --vector \ldots{} --seeds 2 --expand-depth 1 --provenance}.

\begin{lstlisting}[language=TypeScript, caption={Writing linked records and embeddings atomically, then running a hybrid query.}, label=lst:example]
const program = Effect.gen(function* () {
  const db = yield* open("./kb.db");
  yield* db.transaction((ops) => Effect.gen(function* () {
    const paper = yield* ops.records.create({ id: "paper-rag-2020",
      data: { title: "RAG for knowledge-intensive NLP" }, labels: ["Paper"] });
    const survey = yield* ops.records.create({ id: "survey-graphrag",
      data: { title: "Graph RAG: a survey" }, labels: ["Paper"] });
    yield* ops.relationships.create({ type: "CITES",
      sourceId: survey.id, targetId: paper.id });
    yield* ops.vectors.upsert({ recordId: paper.id, vector: [0.9, 0.1, 0.0] });
    yield* ops.vectors.upsert({ recordId: survey.id, vector: [0.2, 0.9, 0.1] });
  }));
  const hits = yield* db.hybrid.search({ vector: [0.1, 1.0, 0.0],
    metric: "cosine", seeds: 1, expandDepth: 1, topN: 5,
    includeProvenance: true });
  // hits[1].provenance: { seedId: "survey-graphrag", graphDepth: 1,
  //   pathCount: 1, pathSummary: "survey-graphrag --CITES--> paper-rag-2020" }
  yield* db.close;
  return hits;
});
\end{lstlisting}

\section{Latency characterization}
\label{sec:characterization}

This section measures the performance of the release on its own. It does not measure answer quality; that is the subject of \cref{sec:design,sec:results}.

\paragraph{Protocol} The harness (\code{packages/benchmark/src/run.ts}) creates a fresh database, generates a synthetic dataset from a linear congruential generator with seed 42, and measures each scenario with 5 discarded warm-up executions followed by 50 measured executions, one at a time in one process. The graph is a chain $r_i \to r_{i+1}$ plus 24 edges from $r_0$ to $r_1,\dots,r_{24}$. Each record has a vector in namespace \code{default} (dimension $d$) and in namespace \code{wide} (dimension $4d$). Percentiles use the nearest-rank method, so with 50 samples p95 is the third-largest and p99 the largest observation. Following~\cite{hoefler2015benchmarking} we report medians as the main statistic and treat tails, which rest on one to three observations, as indicative only. Runs used commit \code{69ca4b2} on an Apple M5 (10 cores, \SI{16}{GB} RAM, macOS) with Node.js 24.13.0, at $N \in \{\num{2500}, \num{10000}\}$ records with $d = 128$, at $N = \num{10000}$ with $d = 384$ (ingestion), and one exact search at $N = \num{10000}$ with $d = 512$.

\paragraph{Results} \Cref{tab:latency,tab:ingestion} and \cref{fig:scaling} summarize the measurements.
\begin{enumerate}
  \item \emph{The exact vector scan dominates.} Multiplying $N$ by 4 multiplies the median exact-search latency by 4.2 (\SI{8.03}{} to \SI{33.95}{ms}), consistent with an $O(N)$ scan. Switching to L2 lowers the median by 4--6\%, and raising $k$ from 10 to 100 raises it by 2--17\%.
  \item \emph{Graph expansion adds little to a hybrid query.} The median of a 2-hop Mode B query exceeds that of plain exact search by \SI{2.4}{ms} at \num{2500} records and by \SI{5.0}{ms} at \num{10000}. These are differences between separately measured scenarios, not per-stage timings.
  \item \emph{BFS should remain the default traversal.} At \num{10000} records BFS is 7.0$\times$ faster than the recursive CTE at 2 hops and 13.1$\times$ faster at 3 hops.
  \item \emph{An unselective filter is pure overhead.} The label filter in the benchmark matches every record, so filtered search is \SIrange{2}{7.5}{ms} slower than unfiltered search; the gain from selective filter-first execution is not measured here.
  \item \emph{Ingestion and storage.} Single-record creates sustain between \num{7300} and \num{7900} records/s, and batches of 25 between \num{13600} and \num{15200} records/s (across the three configurations in \cref{tab:ingestion}). The database file is $2.0\times$ the raw vector bytes at $d = 128$ and $1.4\times$ at $d = 384$.
\end{enumerate}

\paragraph{Threats to validity} The vectors are synthetic and carry no semantic structure, so these results concern cost, not quality. The graph is a chain with one 24-edge hub, so traversal frontiers stay small regardless of $N$. Each configuration was run once, so run-to-run variation is not quantified. Bulk ingestion throughput is computed from two batches of 25 records. Isolated tail values above \SI{390}{ms} are single observations whose cause has not been investigated. Process RSS includes the Node.js runtime and the native Turso library. All results come from one machine and one operating system.

\section{Agent evaluation: design}
\label{sec:design}

\subsection{Question and hypotheses}

The question is whether an AI agent that answers relational retrieval questions with CheguersDB is more accurate than an agent with no database, or with a plain relational store. The study is pre-registered (\code{bench/agent-eval/spec/PREREG.md}), and deviations from that document are listed in \cref{sec:threats}. Hypotheses:
\begin{description}
  \item[H1] \code{cheguers-full} has higher mean F1 than \code{files} on the hop2, hop3 and filter strata.
  \item[H2] \code{cheguers-full} has higher mean F1 than \code{cheguers-vector} on hop2 and hop3, and no difference on hop0 and hop1.
  \item[H3] \code{cheguers-full} is no lower than \code{files} on hop0 (mandatory use adds no accuracy cost on lookups).
\end{description}
Tests are one-sided at $\alpha = 0.05$, with Holm correction~\cite{holm1979} across the six pre-registered comparisons. Repeats are averaged within each scenario before testing, as the pre-registration specifies. The hypothesis that H2 holds on hop0 and hop1 was not tested in a separate comparison; those strata are reported in \cref{tab:f1}.

\subsection{Arms}

All arms run the same model, the same corpus, the same question text, the same embedding function and the same turn budget. The agent is Claude Code running \code{claude-haiku-5-5} through a subscription token, inside a Terminal-Bench~\cite{merrill2026terminalbench} task container.

\begin{description}
  \item[files] The corpus as one JSON Lines file, the embedding helper and an unrestricted shell with Python and grep. No database.
  \item[sqlite3] The same records, edges and vectors loaded into SQLite tables. The agent must answer from that database, through the Python \code{sqlite3} module; it computes cosine similarity itself.
  \item[cheguers-full] The \code{cheguers} CLI with the same data loaded through the library bulk API. The prompt makes CLI use mandatory and lists the commands, including \code{hybrid} with expansion depth 1.
  \item[cheguers-vector] As \code{cheguers-full}, but restricted to \code{vec-search} and \code{hybrid} with expansion depth 0. This ablation isolates graph expansion.
  \item[closed-book] Calibration floor. The agent receives the questions and no data, and must answer from its own knowledge.
  \item[gold-context] Calibration ceiling. The agent receives only the records that support each question (the gold supporting records), and no corpus.
\end{description}

The database arms receive no corpus file. The corpus is loaded into the store at install time and the store is deleted before the agent starts. The files arm receives the corpus as its only data file.

\subsection{Corpus and questions}

A seeded generator (\code{bench/agent-eval/gen/generate.mjs}) builds a corpus of 1,400 papers, 700 authors, 80 organizations and 40 venues: 2,220 records and about 8,500 typed edges (\code{PRESENTED\_AT}, \code{AUTHORED\_BY}, \code{AFFILIATED\_WITH}, \code{CITES}). Each record's text states its relations in prose, so the same facts are available to every arm. About a quarter of papers reuse the topic and setting of an earlier paper, and about 30\% of organization names are near-variants of another name. Questions are paraphrased with synonyms that do not appear in the corpus text, so lexical matching on the question wording does not identify the answer.

Five strata differ by the number of hops from the question's anchor to the answer: hop0 (a paper described by its topic, setting and modifier; the answer is the paper id), hop1 (the paper's venue), hop2 (organizations of the paper's authors), hop3 (organizations of the authors of the papers the paper cites), and filter (venue and affiliation name filters followed by a two-hop traversal). Gold answers are computed from the graph. The hop2 and filter answers are also checked by a second computation over the same edges. The gold file is copied into a task only at scoring time.

A scenario is one seed and one stratum with five questions. Six seeds (1 to 6) give 30 scenarios, so each main arm answers 150 questions per repeat and 450 over three repeats.

\subsection{Scoring and budget}

The primary metric is per-question set-F1 between the agent's answer and the gold set; empty gold sets are not used. Each answer is written to \code{/app/answer.json}. A hidden pytest file computes F1 per question and writes \code{SCORE} lines. Every arm has a 12-turn budget, enforced with the \code{--max-turns} flag of the Claude CLI. A trial that exhausts the budget writes whatever answer it has, so its unanswered questions score zero. Budget exhaustion is therefore counted separately (\cref{tab:failures}) and is a confound for accuracy, not a neutral failure. The budget was chosen from a pilot: at six turns every arm ran out before answering, and at twelve turns files, sqlite3 and \code{cheguers-full} solved the pilot's hardest scenario, while \code{cheguers-vector} still exhausted it.

\subsection{Embedding function and harness}

All arms use all-MiniLM-L6-v2, a sentence-embedding model of the family introduced in~\cite{reimers2019sbert}, through \code{fastembed} 0.9.0 (384 dimensions). Corpus vectors are precomputed on the host and loaded into each database arm; question vectors are computed at run time inside each arm. The model is baked into a base container image, so the embedder is identical in every arm.

Each scenario runs as one Terminal-Bench task with \code{terminal-bench} 0.1.1, one trial per arm per repeat. Before the study, the oracle agent, which writes the gold answers into the answer file, passed all four variants (main, files, gold-context and closed-book) of one task, \code{kb-s1-hop1}. The oracle was not run on the other 116 tasks, which are built by the same script. Concurrency was two containers.

\section{Discussion}
\label{sec:discussion}

\paragraph{Why the baseline is strong} The files arm writes a short Python program that loads the corpus file, matches the paraphrased question to a paper by its structured fields, and walks the relations in code. The model performs the paraphrase-to-term mapping, which is the semantic step, and the join is exact. At 2,220 records this is a small computation for one process, so the corpus never forces a retrieval step. The gold-context ceiling shows the questions are answerable from the records alone, and the closed-book floor shows the answers are not guessable.

\paragraph{What the database adds} In this setting the database does not improve accuracy, and it costs more calls. Graph expansion scored higher than vector-only retrieval on hop2 and hop3, where the vector-only arm struggles, and that difference is nominally significant only before correction. The vector-only arm exhausted its budget most often. Part of that gap is therefore a budget effect, not only a retrieval effect, and we cannot separate the two with this design.

\paragraph{What would test the claim} A fair test needs data where the baseline cannot do the join in one pass. Candidates include a corpus too large to load into one agent context or one process, selective filters, documents that do not reduce to a structured file, and a real multi-hop question-answering set with gold supporting facts. Any such test must be pre-registered and must not reuse the present gold data.

\paragraph{Relation to HybridRAG} HybridRAG reports gains on financial earnings transcripts~\cite{sarmah2024hybridrag}, where the relevant text is unstructured and a script cannot join it. Our corpus has explicit relations and structured fields, the condition under which an exact script matches the store. The two results are compatible: the benefit of hybrid retrieval may depend on whether the relevant structure is recoverable without retrieval.

\section{Impact}
\label{sec:impact}

\paragraph{Reproducible retrieval for RAG} Because the hybrid order is fully specified and every result carries its provenance, an application can store expected contexts for a set of questions and test that a change to data or code does not silently change them.

\paragraph{Embedded memory for agents} The store is a single file inside the application process, so it can serve as persistent memory for local tools without a service to operate. The study here does not show that it improves answers over files for this task.

\paragraph{A research baseline} The harness, generator and gold computation give a reproducible starting point for measuring agents on relational retrieval. The gold answers are computed from the graph rather than written by hand.

\section{Threats to validity and deviations}
\label{sec:threats}

\paragraph{Power and statistics} Six scenarios per stratum give limited power. The intervals in \cref{tab:f1} are wide, and no comparison survives correction at $\alpha = 0.05$. The results support ``no evidence of benefit under these conditions'' and a suggestive ablation effect, not effect sizes that generalize.

\paragraph{Budget confound} The 12-turn budget was chosen from a pilot. The vector-only arm exhausts it on most multi-hop questions, so its accuracy partly reflects the budget. Accuracy at a different budget could differ. The budget was not varied.

\paragraph{Ceiling} The files arm scores at least 0.92 on every stratum, which leaves little room for a better arm to show improvement.

\paragraph{Synthetic and single-model} The corpus and questions are generated, not drawn from a public dataset. One model, one corpus generator, one scorer and one sentence-embedding model were used. The results may not transfer to other models, corpora or embedders.

\paragraph{Deviations from the pre-registration} The pre-registration (\code{bench/agent-eval/spec/PREREG.md}) lists each deviation in full. In summary: (i) the embedder was not fixed in the draft; a lexical hash embedder was used in the first pilot, and all-MiniLM-L6-v2 replaced it before the reported runs; (ii) the \code{cheguers} CLI has no bulk relationship command, so the loader uses the library bulk API; (iii) a first full run placed the corpus inside the database-arm images, so the database arms could read the relations as text; those runs are archived, excluded from every number here, and the reported runs keep the corpus in the deleted store; (iv) a 12-turn budget was added before the reported runs; (v) the retrieval-only comparisons (BM25, MRR, brute-force cosine) planned in the draft were not implemented, so the retrieval evidence is the top-20 proxy only; (vi) the sqlite3 arm uses the Python \code{sqlite3} module rather than the CLI; (vii) Holm correction is applied across all six tests, which is stricter than the draft scheme; (viii) the \code{cheguers} CLI ignores \code{--direction outgoing}, which was documented and not fixed.

\section{Limitations and roadmap}
\label{sec:roadmap}

The exact scan grows linearly with corpus size and takes about \SI{34}{ms} at \num{10000} records. The next step is a rebuildable approximate index, with exact search kept as fallback and recall reference. Filters currently constrain only the seeds; applying them at every expansion hop is needed before the library holds multi-tenant data. Every call takes an immediate transaction, so operations are serialized and there is no concurrent read path. Planned work includes a corpus that the baseline cannot load in one pass, selective filters, a public multi-hop question-answering set with gold supporting facts, and the retrieval-only comparisons that were not implemented here.

\section{Conclusions}

CheguersDB fits the parts of a HybridRAG retriever that are usually spread across two databases (records, relationships, embeddings, filters, traversal and ranking) into one embedded library over one transactional file. Its ranking procedure is deterministic and explains each result, and its costs are measured: at 10,000 records, graph traversal takes about 1 to 2 ms, two-hop hybrid expansion about \SI{39}{ms} and an exact vector scan about \SI{34}{ms}, which grows linearly with corpus size.

On a pre-registered, controlled agent evaluation over synthetic relational questions, the hybrid store did not improve answer accuracy over an agent that reads the same data with Python. The baseline is near the ceiling because a small corpus can be joined exactly in one pass. Graph expansion scored higher than vector-only retrieval on the two deepest strata, a suggestive result that does not survive correction. A claim that CheguersDB helps agents requires a setting in which retrieval is needed, which this study did not test.
